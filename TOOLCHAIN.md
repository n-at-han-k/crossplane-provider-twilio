# The toolchain

This provider is generated by **Twilio's own openapi-generator**, not by one
written here. `reference/twilio-oai-generator` is a submodule, and this repo's
generator is a subclass of `TwilioTerraformGenerator` plus its own templates.

```
reference/twilio-oai/spec/json/twilio_*.json      60 documents (submodule, 2.8.3)
reference/twilio-oai-generator                    Twilio's generator (submodule, 0150189d)
  → mvn package → target/twilio-openapi-generator.jar   a SHADED jar, 28 MB
generators/twilio                                 our subclass + templates
  → javac against that jar → crossplane-codegen.jar
  → java -cp ours:theirs org.openapitools.codegen.OpenAPIGenerator batch
  → goimports, controller-gen, angryjet
```

## Why this instead of our own generator

`crossplane-provider-rt` and `crossplane-provider-orangehrm` each carry a
generator written here, extending upstream openapi-generator's
`terraform-provider` generator, because nobody else had described those APIs.
Twilio has, and its generator already answers the questions that were the
whole difficulty in the other two:

| | where it comes from |
|---|---|
| which operations are one resource | `resourceId` = path minus extension, minus trailing param, minus param names |
| which is the create, read, update, delete | `Utility.populateCrudOperations` — the `operationId` prefix |
| what the external name is | `x-resource-id`, the fetch's last path param, and the resource is dropped if it is not in the response body |
| snake_case of any name | `StringHelper.toSnakeCase`, four passes |
| a field settable only on update | `x-update-after-create` |
| an int id needing a string | `x-resource-id-conversion-func` |
| a read keyed on a query parameter | `has-fetch-with-query-params` |
| instance vs list path | `PathUtils.isInstanceOperation` — `x-twilio.pathType`, falling back to a trailing `}` |
| form encoding, SID types, nullables | the Go generators and `terraform-provider-twilio/core` |

Every one of those was an item in PLAN.md's "what Twilio breaks". Writing them
again, in our own Java, against the same document, to get the same answers, is
work whose best possible outcome is a tie.

## The two pins, and why they are what they are

### The generator: `0150189d` (2024-05-17), not `main`

**The terraform generator on `main` is dead.** Run it — by hand, or through
Twilio's own `scripts/build_twilio_library.py` — and it writes
`.openapi-generator/FILES` and nothing else. `resources` comes back empty, so
`clearTemplateFiles()` fires and `api.mustache` never runs. Neither the
current spec nor the 1.56.1 spec produces a single `.go` file.

It is not spec drift. `TwilioTerraformGenerator` and its templates were last
touched **2023-08-30**; `DirectoryStructureService`, the shared machinery it
depends on, has changed 12 times since. terraform-provider-twilio is marked
"PILOT and NOT under active development", and its generator path rotted with
it.

`0150189d` is a commit where it works, chosen because it is the last one
before the provider's final release (0.18.46, 2024-06-06).

**The pin is verified, not assumed.** At generator `0150189d` and spec
`1.56.1`, the pipeline reproduces terraform-provider-twilio's committed
`twilio/resources/api/v2010/api_default.go` — 2745 lines — **byte for byte
after `goimports`**:

```bash
cd reference/twilio-oai-generator
mvn package -DskipTests
python3 scripts/build_twilio_library.py <1.56.1 spec>/twilio_api_v2010.json /tmp/out -l terraform
goimports -w /tmp/out/twilio/resources/api/v2010/api_default.go
diff /tmp/out/twilio/resources/api/v2010/api_default.go \
     ../terraform-provider-twilio/twilio/resources/api/v2010/api_default.go   # empty
```

That is the useful kind of pin: it is not "a commit that compiled", it is a
commit that provably produces the artefact Twilio shipped. Anything our
generator gets wrong from here is ours.

The raw generated file is spaces-indented with unsorted imports and no `fmt`
or `strings`, so `goimports` is part of the pipeline rather than a tidy-up --
which is what `bin/generate` already does for the same reason.

### The spec: current (`2.8.3`), not the pinned one

The 1.56.1 pin exists only to verify the generator against the provider. The
provider we ship is generated from the **current** document, and the 2024
generator handles it: 37 products produce a resource file from today's
`spec/json`. Nothing forces us backwards.

`hack/parity.py` still needs 1.56.1 to compare against
terraform-provider-twilio, because that is the document the provider was built
from; see PARITY.md.

## What has to be built on top

The public generator stops short of a whole repo. `terraform-provider-twilio`'s
`twilio/resources/resources.go` — the registry of all 164 resources — is in no
template here, and its commits say `[Librarian] Regenerated @ <sha>`: Twilio
aggregates across documents with an internal tool.

So the cross-document steps are ours, which is the same conclusion PLAN.md
reached from the other direction. Concretely:

- one openapi-generator **batch** run over per-document configs, the way
  `build_twilio_library.py` does it — each document is still a separate
  generation writing its own files, so batch does not solve aggregation, it
  only avoids 60 JVM starts;
- the registrations that must name every Kind in the repo —
  `internal/controller/twilio.go`, `apis/twilio.go` — generated from the
  output tree after the batch, not by a template that can only see one
  document;
- the scaffold that is per-repo rather than per-document: `cmd/provider`, the
  `ProviderConfig`, `Makefile`, `package/crossplane.yaml`.

## Building it here

No JDK or Maven on the host; both come from the flake. The jar is shaded --
Twilio's own script runs `java -cp target/twilio-openapi-generator.jar` with
nothing else on the classpath -- so it carries openapi-generator 7.13.0 inside
it and **we do not depend on nixpkgs' `openapi-generator-cli`**. That also
removes a version-skew failure: nixpkgs tracks openapi-generator's latest,
their classes are compiled against 7.13.0, and a mismatch there is a
`NoSuchMethodError` at generate time.

Their sources use lombok, but only to compile. Compiling *our* subclass against
their *jar* needs no annotation processing, so `javac` against the shaded jar
is enough -- the same shape as RT's flake, one jar further along.
